# Feature Plan: Project Goal Future Value and Track Status (FR13.4)

**Feature ID:** FR13.4  
**Status:** 📝 Proposed / Planned  
**Title:** Project Goal Future Value and Track Status  
**User Story:** As a user tracking a financial goal, I want to see a projection of my linked assets' future value based on their current performance (XIRR), and have the system calculate if I am "On Track" or "Off Track" to meet my goal, so that I can see the long-term impact of my investments.

---

## 1. Mathematical Design & Compound Growth Formulas

To project the future value of linked assets and determine if a goal is on track, the system must execute two primary computations:
1. Calculate the **combined XIRR (historical return)** of all linked assets.
2. Calculate the **Projected Future Value** at the goal's target date and compare it with the target amount.

### 1.1. Combined XIRR Calculation
We compile all historical transactions and current valuations across all linked portfolios and assets into a single list of cash flows.
* **Cash Flow Compilation:**
  * For each linked **portfolio**:
    * Retrieve all standard transactions, Fixed Deposits (FDs), and Recurring Deposits (RDs).
    * Convert their transaction quantities/prices to cash inflows (negative values) and outflows (positive values representing dividends, coupons, etc.) using `_get_portfolio_cash_flows`.
    * Get the sum of current market values of all holdings inside the portfolio as a positive cash flow at `date.today()`.
  * For each linked **asset**:
    * Retrieve all user transactions for that asset across all portfolios.
    * Convert them to cash flows.
    * Get the sum of current market values of that specific asset holding across all user portfolios as a positive cash flow at `date.today()`.
* **XIRR Formula:**
  We solve for the annual rate $r$ in the NPV equation:
  $$NPV = \sum_{j=1}^{M} \frac{C_j}{(1 + r)^{\frac{d_j - d_1}{365}}} = 0$$
  *Where $C_j$ is the cash flow amount on date $d_j$, and $d_1$ is the first cash flow date.*
* **Bounds and Fallback Returns:**
  If the calculated combined XIRR is unavailable (e.g., insufficient cash flows), negative ($XIRR \le 0$), or extremely high ($XIRR > 1.0$, i.e. $>100\%$), it is considered an extreme outlier due to short-term volatility or data anomalies. In these cases:
  * **Fallback Rate:** Stored `expected_return` for the goal (if set), else the default rate **10.0%**.

### 1.2. Projected Future Value ($PV_{\text{future}}$)
We compound the total current value ($PV$, or `current_amount`) of all linked items to the target date using the determined annual rate of return ($r$ as percentage, e.g. 12.0%).
* **Formula:**
  $$PV_{\text{future}} = PV \times (1 + i)^N$$
  * **$i$ (Monthly Interest Rate):** $i = \frac{r}{12 \times 100}$
  * **$N$ (Months remaining):** $N = \max\left(0.0, \frac{(\text{target\_date} - \text{current\_date}).days}{30.4375}\right)$

### 1.3. Status Determination
* **On Track:** Stored as `status = "On Track"` if $PV_{\text{future}} \ge \text{target\_amount}$.
* **Off Track:** Stored as `status = "Off Track"` if $PV_{\text{future}} < \text{target\_amount}$.

### 1.4. Projection Chart Data Points
The chart displays two trajectories from today to the goal's target date ($M$ months). We generate quarterly/monthly intervals:
1. **Projected Path (Current Investments Growth):**
   $$Value_{\text{proj}}(m) = PV \times (1 + i)^m$$
2. **Target Path (Growth with Required SIP):**
   $$Value_{\text{target}}(m) = PV \times (1 + i)^m + SIP \times \frac{(1 + i)^m - 1}{i}$$
   *(If $i = 0$, $Value_{\text{target}}(m) = PV + SIP \times m$)*

## 2. Backend Architecture

### 2.1. API endpoint additions
We will modify the single goal detail endpoint `/api/v1/goals/{goal_id}` to return the updated analytics payload.

### 2.2. Schemas (`backend/app/schemas/goal.py`)
Modify `GoalWithAnalytics` to include the following fields:
* `linked_assets_xirr: float` (the calculated combined XIRR rate, e.g. `12.34` or `0.0`)
* `projected_future_value: float` (projected value of current holdings at target date)
* `status: str` (`"On Track"` or `"Off Track"`)
* `projection_chart_data: List[GoalProjectionPoint]`
Where `GoalProjectionPoint` is:
```python
class GoalProjectionPoint(BaseModel):
    date: str # YYYY-MM-DD
    projected_value: float
    target_value: float
```

### 2.3. CRUD Logic (`backend/app/crud/crud_goal.py`)
We will rewrite `get_goal_with_analytics`:
1. Compile all transaction cash flows for linked assets and portfolios (deduplicating linked items).
2. Calculate the combined XIRR using `_calculate_xirr`.
3. If `0.0 < combined_xirr <= 1.0`, use it as `calculated_return_rate`. Otherwise, fallback to the goal's `expected_return` or `10.0`.
4. Calculate the required SIP using the same `calculated_return_rate`.
5. Compute the projected future value at target date.
6. Determine the on-track/off-track status.
7. Generate projection chart points (12-36 points maximum, e.g., monthly for goals < 2 years, quarterly for goals up to 5 years, and yearly for goals > 5 years, to ensure chart clean rendering).

## 4. Database & Column Encryption
* **Database Updates:** No schema migrations are required because all projection parameters are computed dynamically at runtime based on active asset transactions.
* **Column Encryption:** SQLite columns in `goals` and `goal_links` do not store any sensitive data (credentials, tokens, personal identifiers). Consequently, **no column encryption is required** for the database tables related to this feature.

---

## 5. Required Datasources
The calculation pulls data at runtime from:
1. **Goals Database:** Stored name, target amount, expected return, and target date.
2. **Goal Links:** Linked portfolios and assets.
3. **Portfolio Transactions:** Historical buy/sell/corporate actions transactions.
4. **Market Data:** Current market valuations of stocks/mutual funds to calculate current asset value (representing the final cash flow for XIRR).

---

## 6. Android Compatibility & Python Libraries
* **Android Library:** The application uses **Chaquopy** to run Python in Android.
* **Dependency Analysis:** Native wheels containing C/Rust code like `pyxirr` can fail on Android. However, `crud_analytics.py` has an automated fallback mechanism:
  * If `pyxirr` is missing, it falls back to a pure-Python Newton-Raphson method relying on `numpy` (which is fully supported by Chaquopy).
* **Decision:** We reuse the existing `_calculate_xirr` fallback engine. No external libraries are introduced, guaranteeing complete Android compatibility.
